# Requirements Document

## Introduction

FreeNode Dashboard is a full-stack web application built on top of an existing Pterodactyl panel installation. It provides a user-facing dashboard where players and developers can sign in with Discord, earn coins through AFK farming and ad link engagement, redeem codes, and spend coins to create and renew free game or bot servers. An admin panel gives operators full control over resource limits, coin rates, eggs, shop items, and user management. The system ships with a one-command interactive bash installer for Ubuntu 20.04/22.04 VPS environments.

## Glossary

- **Dashboard**: The FreeNode web application as a whole
- **User**: An authenticated person who has logged in via Discord OAuth2
- **Admin**: A User whose Discord ID appears in the ADMIN_DISCORD_IDS environment variable or is flagged as admin in the database
- **Pterodactyl**: The existing game server management panel the Dashboard wraps
- **Pterodactyl_Service**: The internal axios-based wrapper that communicates with the Pterodactyl Application and Client APIs
- **Auth_Service**: The Passport.js Discord OAuth2 authentication layer
- **Coin_Service**: The internal service responsible for crediting, debiting, and validating coin balances
- **AFK_Service**: The server-side handler for passive coin earning via the AFK page
- **Earn_Service**: The server-side handler for ad-link-based coin earning
- **Redeem_Service**: The service that validates and applies redeem codes
- **Shop_Service**: The service that processes resource upgrade purchases
- **Expiry_Service**: The cron-based service that suspends and deletes expired servers
- **Installer**: The install.sh bash script that sets up the Dashboard on a fresh VPS
- **Egg**: A Pterodactyl server template defining the software stack (e.g., Minecraft, Node.js bot)
- **Node**: A Pterodactyl physical host that servers are allocated on
- **Allocation**: An IP:port pair on a Node available for server assignment
- **Coins**: The virtual currency earned and spent within the Dashboard
- **Redeem_Code**: A string token that grants coins or resource bonuses when applied by a User
- **Shop_Item**: A purchasable resource upgrade available in the shop
- **Earn_Link**: An ad or offer link configured by an Admin that Users can complete for coins
- **Session**: An express-session backed by a MySQL session store
- **CSRF_Token**: A token generated by csurf to protect state-changing requests
- **Rate_Limiter**: The express-rate-limit middleware applied to sensitive endpoints
- **Settings**: A flat key-value table in MySQL storing all global configuration values

### Requirement 1: Installer Script

**User Story:** As a server operator, I want a single command to install and configure the Dashboard, so that I can get the system running without manual setup steps.

#### Acceptance Criteria

1. WHEN the operator runs `bash install.sh`, THE Installer SHALL verify that the host OS is Ubuntu 20.04 or 22.04 before proceeding.
2. WHEN the OS check passes, THE Installer SHALL verify that Node.js version 18 or higher is installed.
3. WHEN the Node.js check passes, THE Installer SHALL verify that MySQL or MariaDB is installed and reachable.
4. WHEN the MySQL check passes, THE Installer SHALL verify that PM2 is installed globally.
5. WHEN the PM2 check passes, THE Installer SHALL verify that Nginx is installed.
6. IF any system requirement check fails, THEN THE Installer SHALL print a descriptive error message identifying the missing dependency and exit with a non-zero status code.
7. WHEN all system checks pass, THE Installer SHALL interactively prompt the operator for the following ten values: Pterodactyl Panel URL, Application API Key, Client API Key, Discord Client ID, Discord Client Secret, Discord Bot Token, Discord Guild ID, Dashboard URL, MySQL root password, and database name.
8. WHEN all prompts are answered, THE Installer SHALL create a MySQL database and dedicated database user with the provided credentials.
9. WHEN the database is created, THE Installer SHALL generate a `.env` file from `.env.example` populated with all provided values.
10. WHEN the `.env` file is written, THE Installer SHALL run `npm install` to install all dependencies.
11. WHEN dependencies are installed, THE Installer SHALL run the database migration to create all required tables.
12. WHEN the migration completes, THE Installer SHALL seed the Settings table with default configuration values.
13. WHEN seeding completes, THE Installer SHALL register the application with PM2 using `ecosystem.config.js`.
14. WHEN PM2 registration completes, THE Installer SHALL prompt the operator whether to configure Nginx as a reverse proxy.
15. WHERE the operator opts into Nginx configuration, THE Installer SHALL write an Nginx server block for the Dashboard URL and reload Nginx.
16. WHERE the operator opts into SSL, THE Installer SHALL invoke Certbot to obtain and configure a TLS certificate for the Dashboard URL.
17. WHEN all steps complete, THE Installer SHALL print a summary showing the Dashboard URL, admin panel URL, and PM2 process name.

### Requirement 2: Discord OAuth2 Authentication

**User Story:** As a visitor, I want to log in with my Discord account, so that I can access the Dashboard without creating a separate account.

#### Acceptance Criteria

1. WHEN a visitor navigates to `/auth/discord`, THE Auth_Service SHALL redirect the visitor to Discord's OAuth2 authorization endpoint with scopes `identify`, `guilds`, and `guilds.members.read`.
2. WHEN Discord redirects back with an authorization code, THE Auth_Service SHALL exchange the code for an access token and retrieve the user's Discord profile.
3. WHERE `REQUIRED_GUILD_ID` is set, WHEN a User completes OAuth2, THE Auth_Service SHALL verify that the User is a member of the specified Discord guild.
4. IF the guild membership check fails, THEN THE Auth_Service SHALL redirect the User to the login page with an error message stating they must join the required server.
5. WHEN a User authenticates for the first time, THE Auth_Service SHALL create a Pterodactyl account for the User via the Pterodactyl_Service using the User's Discord email and a generated password.
6. WHEN a User authenticates for the first time, THE Auth_Service SHALL insert a User record into the database with the Discord ID, username, avatar hash, Pterodactyl user ID, zero coin balance, default resource limits, and admin flag set to false.
7. WHEN a returning User authenticates, THE Auth_Service SHALL update the User's Discord username and avatar hash in the database.
8. WHEN authentication succeeds, THE Auth_Service SHALL establish a Session for the User and redirect to `/dashboard`.
9. WHEN a User navigates to `/auth/logout`, THE Auth_Service SHALL destroy the Session and redirect to the login page.
10. IF a suspended User attempts to authenticate, THEN THE Auth_Service SHALL redirect the User to the login page with a suspension notice.

### Requirement 3: User Dashboard

**User Story:** As a User, I want a dashboard home page, so that I can see my coin balance, server statuses, and quick access to earning features.

#### Acceptance Criteria

1. WHILE a User is authenticated, THE Dashboard SHALL display the User's Discord avatar, username, and current coin balance in a welcome bar.
2. WHEN the dashboard page loads, THE Dashboard SHALL fetch and display a card for each server owned by the User, showing server name, status, RAM, CPU, disk, and expiry countdown.
3. WHEN the dashboard page loads, THE Dashboard SHALL display a quick stats bar showing total servers owned, coins earned today, and next expiry date.
4. WHEN the dashboard page loads, THE Dashboard SHALL display shortcut links to the AFK page, Earn page, Redeem page, and Shop page.
5. IF a User has no servers, THEN THE Dashboard SHALL display a prompt encouraging the User to create their first server.

### Requirement 4: Server Creation

**User Story:** As a User, I want to create a free game or bot server, so that I can host my project without paying for hosting.

#### Acceptance Criteria

1. WHEN a User submits the server creation form, THE Dashboard SHALL validate that the User has not exceeded their maximum server slot limit.
2. WHEN a User submits the server creation form, THE Dashboard SHALL validate that the User has sufficient coins to cover the creation cost defined in Settings.
3. WHEN a User submits the server creation form, THE Dashboard SHALL validate that the selected Egg is enabled in the Admin eggs configuration.
4. WHEN a User submits the server creation form, THE Dashboard SHALL validate that the requested RAM, CPU, and disk values do not exceed the User's remaining resource allowance.
5. WHEN a User submits the server creation form, THE Dashboard SHALL validate that an available Allocation exists on the selected Node.
6. IF any validation fails, THEN THE Dashboard SHALL return the form with a descriptive error message identifying the specific validation failure.
7. WHEN all validations pass, THE Pterodactyl_Service SHALL create the server via the Pterodactyl Application API with the specified Egg, Node, Allocation, and resource values.
8. WHEN the Pterodactyl API confirms server creation, THE Coin_Service SHALL deduct the creation cost from the User's coin balance.
9. WHEN the coin deduction succeeds, THE Dashboard SHALL insert a Server record into the database with the Pterodactyl server ID, owner User ID, expiry timestamp calculated from the Settings renewal period, and status set to active.
10. WHEN the server record is saved, THE Dashboard SHALL redirect the User to their server list with a success message.
11. IF the Pterodactyl API returns an error during creation, THEN THE Dashboard SHALL display an error message and SHALL NOT deduct coins from the User's balance.

### Requirement 5: Server Renewal

**User Story:** As a User, I want to renew my server before it expires, so that I can keep it running without losing my data.

#### Acceptance Criteria

1. WHEN a User requests renewal of a server, THE Dashboard SHALL verify that the server record belongs to the requesting User.
2. WHEN ownership is confirmed, THE Dashboard SHALL validate that the User has sufficient coins to cover the renewal cost defined in Settings.
3. IF the User has insufficient coins, THEN THE Dashboard SHALL return an error message stating the required coin amount.
4. WHEN the coin check passes, THE Coin_Service SHALL deduct the renewal cost from the User's coin balance.
5. WHEN the deduction succeeds, THE Dashboard SHALL extend the server's expiry timestamp by the renewal period defined in Settings.
6. IF the server is currently suspended due to expiry, THEN THE Pterodactyl_Service SHALL unsuspend the server after the expiry is extended.
7. WHEN renewal completes, THE Dashboard SHALL return a success response with the new expiry timestamp.

---

### Requirement 6: Server Expiry Cron

**User Story:** As an operator, I want expired servers to be automatically suspended and eventually deleted, so that resources are reclaimed without manual intervention.

#### Acceptance Criteria

1. THE Expiry_Service SHALL run a cron job every 15 minutes.
2. WHEN the cron job runs, THE Expiry_Service SHALL query all Server records whose expiry timestamp is in the past and whose status is active.
3. WHEN an expired active server is found, THE Pterodactyl_Service SHALL suspend the server via the Pterodactyl Application API.
4. WHEN suspension succeeds, THE Expiry_Service SHALL update the Server record status to suspended.
5. WHEN the cron job runs, THE Expiry_Service SHALL query all Server records whose status is suspended and whose expiry timestamp is older than the deletion grace period defined in Settings.
6. WHEN a server exceeds the deletion grace period, THE Pterodactyl_Service SHALL delete the server via the Pterodactyl Application API.
7. WHEN deletion succeeds, THE Expiry_Service SHALL remove the Server record from the database.
8. WHERE `DISCORD_BOT_TOKEN` is configured, WHEN a server is suspended, THE Expiry_Service SHALL send a Discord DM to the server owner notifying them of the suspension and renewal instructions.
9. IF the Pterodactyl API returns an error during suspension or deletion, THEN THE Expiry_Service SHALL log the error with the server ID and continue processing remaining servers.

### Requirement 7: AFK Coin Farming

**User Story:** As a User, I want to earn coins by keeping the AFK page open, so that I can accumulate coins passively over time.

#### Acceptance Criteria

1. WHILE a User has the AFK page open, THE AFK_Service SHALL accept a POST request to `/afk/ping` every 60 seconds from the client.
2. WHEN a ping is received, THE AFK_Service SHALL validate that the User has not exceeded the daily AFK coin earning limit defined in Settings.
3. WHEN the daily limit check passes, THE Coin_Service SHALL credit the User's balance with the per-ping coin amount defined in Settings.
4. WHEN the coin credit succeeds, THE AFK_Service SHALL return the User's updated coin balance and remaining daily allowance.
5. IF the daily limit is reached, THEN THE AFK_Service SHALL return a response indicating the limit is reached and SHALL NOT credit additional coins.
6. WHEN the AFK page has been open for the interval defined in Settings without a CAPTCHA verification, THE AFK_Service SHALL respond to the next ping with a CAPTCHA challenge flag.
7. WHEN a CAPTCHA challenge is active, THE AFK_Service SHALL NOT credit coins for pings until the User submits a correct CAPTCHA response to `/afk/captcha-verify`.
8. WHEN a User submits a correct CAPTCHA response, THE AFK_Service SHALL clear the CAPTCHA challenge state and resume crediting coins.
9. IF a User submits an incorrect CAPTCHA response, THEN THE AFK_Service SHALL return an error and SHALL maintain the CAPTCHA challenge state.
10. THE Rate_Limiter SHALL restrict `/afk/ping` to a maximum of 2 requests per 70 seconds per User session.

### Requirement 8: Earn via Ad Links

**User Story:** As a User, I want to earn coins by completing ad links, so that I can earn larger coin amounts than AFK farming provides.

#### Acceptance Criteria

1. WHEN a User loads the Earn page, THE Earn_Service SHALL display all active Earn_Links with their coin reward, cooldown period, and current availability status for the requesting User.
2. WHEN a User initiates an Earn_Link by posting to `/earn/:link_id/start`, THE Earn_Service SHALL verify the Earn_Link is active and the User's cooldown for that link has expired.
3. IF the cooldown has not expired, THEN THE Earn_Service SHALL return the remaining cooldown time in seconds and SHALL NOT redirect the User.
4. WHEN the cooldown check passes, THE Earn_Service SHALL record a pending earn attempt and redirect the User to the ad link URL.
5. WHEN a User posts to `/earn/:link_id/verify`, THE Earn_Service SHALL validate the completion token returned by the ad provider.
6. WHEN the token is valid, THE Coin_Service SHALL credit the User's balance with the Earn_Link's coin reward.
7. WHEN the credit succeeds, THE Earn_Service SHALL record the completion timestamp for the User and Earn_Link combination to enforce the cooldown.
8. IF the completion token is invalid, THEN THE Earn_Service SHALL return an error and SHALL NOT credit coins.
9. THE Rate_Limiter SHALL restrict `/earn/:link_id/start` to a maximum of 10 requests per hour per User session.

---

### Requirement 9: Redeem Codes

**User Story:** As a User, I want to redeem codes for coins and resource bonuses, so that I can receive rewards from promotions or giveaways.

#### Acceptance Criteria

1. WHEN a User submits a redeem code, THE Redeem_Service SHALL look up the Redeem_Code record by the submitted string in a case-insensitive match.
2. IF the Redeem_Code does not exist, THEN THE Redeem_Service SHALL return an error message stating the code is invalid.
3. IF the Redeem_Code has an expiry timestamp that is in the past, THEN THE Redeem_Service SHALL return an error message stating the code has expired.
4. IF the Redeem_Code has a maximum use count and that count has been reached, THEN THE Redeem_Service SHALL return an error message stating the code has been fully redeemed.
5. IF the Redeem_Code is single-use and the requesting User has already redeemed it, THEN THE Redeem_Service SHALL return an error message stating the code has already been used by this account.
6. WHEN all validations pass, THE Coin_Service SHALL credit the User's balance with the coin amount defined on the Redeem_Code.
7. WHEN the coin credit succeeds, THE Redeem_Service SHALL apply any resource bonuses defined on the Redeem_Code to the User's resource limits.
8. WHEN bonuses are applied, THE Redeem_Service SHALL increment the Redeem_Code's use count and record the User ID in the redemption log.
9. WHEN redemption completes, THE Redeem_Service SHALL return a success message listing the coins and resources received.
10. THE Rate_Limiter SHALL restrict redeem submissions to a maximum of 5 requests per 10 minutes per User session.

### Requirement 10: Shop — Resource Upgrades

**User Story:** As a User, I want to buy permanent resource upgrades with coins, so that I can increase my server capacity over time.

#### Acceptance Criteria

1. WHEN a User loads the Shop page, THE Shop_Service SHALL display all active Shop_Items with their name, description, coin cost, and the resource amount they grant.
2. WHEN a User purchases a Shop_Item, THE Shop_Service SHALL validate that the User has sufficient coins to cover the item's cost.
3. IF the User has insufficient coins, THEN THE Shop_Service SHALL return an error message stating the required coin amount.
4. WHEN the coin check passes, THE Coin_Service SHALL deduct the item cost from the User's coin balance.
5. WHEN the deduction succeeds, THE Shop_Service SHALL apply the resource bonus defined on the Shop_Item to the User's resource limits in the database.
6. WHEN the resource update succeeds, THE Shop_Service SHALL return a success message confirming the purchase and displaying the User's updated resource limits.
7. IF the database update fails after coin deduction, THEN THE Shop_Service SHALL refund the deducted coins and return an error message.

### Requirement 11: Admin Panel — User Management

**User Story:** As an Admin, I want to view and manage all users, so that I can enforce rules and assist users with account issues.

#### Acceptance Criteria

1. WHEN an Admin navigates to `/admin/users`, THE Dashboard SHALL display a paginated table of all Users showing Discord username, Discord ID, coin balance, server count, registration date, and account status.
2. WHEN an Admin searches by Discord username or ID, THE Dashboard SHALL filter the user table to matching records.
3. WHEN an Admin edits a User's coin balance, THE Coin_Service SHALL apply the delta and record a transaction with the Admin's ID as the actor.
4. WHEN an Admin suspends a User, THE Dashboard SHALL set the User's suspended flag to true and destroy any active Session for that User.
5. WHEN an Admin unsuspends a User, THE Dashboard SHALL set the User's suspended flag to false.
6. WHEN an Admin deletes a User, THE Dashboard SHALL delete the User record, all associated Server records, and the corresponding Pterodactyl account via the Pterodactyl_Service.
7. THE Dashboard SHALL restrict all `/admin/*` routes to Users whose Admin flag is true, returning HTTP 403 for all other requests.

### Requirement 12: Admin Panel — Server Management

**User Story:** As an Admin, I want to view and manage all servers, so that I can handle abuse, extend servers, and perform maintenance.

#### Acceptance Criteria

1. WHEN an Admin navigates to `/admin/servers`, THE Dashboard SHALL display a paginated table of all Server records showing server name, owner username, Egg, Node, resource allocation, status, and expiry date.
2. WHEN an Admin suspends a server, THE Pterodactyl_Service SHALL suspend the server and THE Dashboard SHALL update the Server record status to suspended.
3. WHEN an Admin unsuspends a server, THE Pterodactyl_Service SHALL unsuspend the server and THE Dashboard SHALL update the Server record status to active.
4. WHEN an Admin deletes a server, THE Pterodactyl_Service SHALL delete the server and THE Dashboard SHALL remove the Server record from the database.
5. WHEN an Admin extends a server's expiry, THE Dashboard SHALL update the Server record's expiry timestamp by the specified number of days.
6. WHEN an Admin reinstalls a server, THE Pterodactyl_Service SHALL trigger a reinstall via the Pterodactyl Application API.

### Requirement 13: Admin Panel — Eggs Configuration

**User Story:** As an Admin, I want to control which Pterodactyl eggs are available for server creation, so that I can limit offerings to supported software.

#### Acceptance Criteria

1. WHEN an Admin navigates to `/admin/eggs`, THE Dashboard SHALL fetch all Nests and Eggs from the Pterodactyl Application API via the Pterodactyl_Service and display them in a list.
2. WHEN an Admin enables an Egg, THE Dashboard SHALL store the Egg ID in the enabled eggs list in Settings and make it available on the server creation form.
3. WHEN an Admin disables an Egg, THE Dashboard SHALL remove the Egg ID from the enabled eggs list and prevent new servers from being created with that Egg.
4. WHEN an Admin sets default resource values for an Egg, THE Dashboard SHALL store the default RAM, CPU, disk, and startup command in Settings keyed by Egg ID.

---

### Requirement 14: Admin Panel — Redeem Code Management

**User Story:** As an Admin, I want to create and manage redeem codes, so that I can run promotions and reward users.

#### Acceptance Criteria

1. WHEN an Admin creates a single Redeem_Code, THE Dashboard SHALL store the code string, coin reward, resource bonuses, maximum use count, and optional expiry timestamp in the database.
2. WHEN an Admin bulk-generates codes, THE Dashboard SHALL generate the specified quantity of unique Redeem_Code strings and insert them all with the provided reward parameters.
3. WHEN an Admin deactivates a Redeem_Code, THE Dashboard SHALL set the code's maximum use count to its current use count, preventing further redemptions.
4. WHEN an Admin views the codes list, THE Dashboard SHALL display each code with its use count, maximum use count, expiry date, and creation date.

---

### Requirement 15: Admin Panel — Coin Management

**User Story:** As an Admin, I want to give, take, and broadcast coins, so that I can reward users and correct balance errors.

#### Acceptance Criteria

1. WHEN an Admin gives or takes coins from a specific User, THE Coin_Service SHALL apply the delta to the User's balance and record a CoinTransaction with the Admin's Discord ID as the actor and a reason string.
2. WHEN an Admin broadcasts a coin amount to all Users, THE Coin_Service SHALL credit every User record with the specified amount and record a CoinTransaction for each User.
3. WHEN an Admin views the transaction log, THE Dashboard SHALL display a paginated list of CoinTransactions showing actor, recipient, amount, reason, and timestamp.

---

### Requirement 16: Admin Panel — Settings

**User Story:** As an Admin, I want to configure all global settings from the admin panel, so that I can tune the system without editing files.

#### Acceptance Criteria

1. WHEN an Admin navigates to `/admin/settings`, THE Dashboard SHALL display a form populated with all current values from the Settings table.
2. WHEN an Admin saves settings, THE Dashboard SHALL validate that numeric fields contain valid positive numbers and that URL fields contain valid URLs.
3. IF validation fails, THEN THE Dashboard SHALL return the form with error messages identifying each invalid field.
4. WHEN validation passes, THE Dashboard SHALL update all changed Settings records in the database.
5. THE Settings table SHALL store at minimum: server creation coin cost, renewal coin cost, renewal period in days, deletion grace period in days, AFK coins per ping, AFK daily limit, AFK CAPTCHA interval in minutes, maximum servers per user, default RAM limit, default CPU limit, default disk limit, and enabled egg IDs.

### Requirement 17: Pterodactyl API Service

**User Story:** As a developer, I want a centralized Pterodactyl API wrapper, so that all panel interactions go through a single auditable service layer.

#### Acceptance Criteria

1. THE Pterodactyl_Service SHALL expose the following operations: `createUser`, `deleteUser`, `createServer`, `suspendServer`, `unsuspendServer`, `deleteServer`, `reinstallServer`, `getServerDetails`, `getAllNodes`, `getAllNests`, `getAllEggs`, `getAvailableAllocations`, and `getServerResourceUsage`.
2. THE Pterodactyl_Service SHALL use the Application API key for all administrative operations and the Client API key for resource usage queries.
3. IF the Pterodactyl API returns an HTTP 4xx or 5xx response, THEN THE Pterodactyl_Service SHALL throw a structured error object containing the HTTP status code, the Pterodactyl error message, and the originating operation name.
4. THE Pterodactyl_Service SHALL never expose API keys in any HTTP response sent to clients.
5. THE Pterodactyl_Service SHALL set a request timeout of 10 seconds on all outbound API calls.

### Requirement 18: Security Controls

**User Story:** As an operator, I want the Dashboard to enforce security best practices, so that user data and server credentials are protected.

#### Acceptance Criteria

1. THE Dashboard SHALL use `helmet` middleware on all routes to set secure HTTP response headers.
2. THE Dashboard SHALL apply CSRF token validation to all state-changing POST, PUT, PATCH, and DELETE requests.
3. THE Dashboard SHALL use parameterized queries via `mysql2` for all database interactions.
4. THE Dashboard SHALL store Sessions in a MySQL-backed session store using `express-mysql-session`.
5. THE Dashboard SHALL apply `express-rate-limit` middleware to all authentication endpoints, restricting each IP to 20 requests per 15 minutes.
6. THE Dashboard SHALL validate and sanitize all user-supplied input using `express-validator` before processing.
7. THE Dashboard SHALL never include Pterodactyl API keys, the session secret, or database credentials in any client-facing HTTP response or rendered view.
8. WHEN a request reaches any `/admin/*` route, THE Dashboard SHALL verify the requesting User's admin flag before executing the handler, returning HTTP 403 if the flag is false or the User is not authenticated.

### Requirement 19: UI Theme and Responsiveness

**User Story:** As a User, I want a visually consistent dark-themed interface, so that the Dashboard feels polished and is easy to use on any device.

#### Acceptance Criteria

1. THE Dashboard SHALL apply a dark gaming-inspired color scheme using background color `#0d0f14`, card color `#161922`, accent color `#5865F2`, success color `#57F287`, warning color `#FEE75C`, and danger color `#ED4245` across all views.
2. THE Dashboard SHALL use Outfit or Plus Jakarta Sans as the primary font and Inter as the secondary font.
3. THE Dashboard SHALL render a collapsible sidebar navigation present on all authenticated pages.
4. THE Dashboard SHALL apply glassmorphism card styling to server cards and stat panels.
5. THE Dashboard SHALL render all pages correctly on viewport widths from 320px to 1920px without horizontal scrolling.
6. THE Dashboard SHALL apply page-specific accent colors: deep space tones for the AFK page, gold tones for the Shop page, green tones for the Earn page, and purple tones for the Redeem page.

---

### Requirement 20: Session and Process Management

**User Story:** As an operator, I want the Dashboard to run reliably under PM2 and restart automatically, so that brief errors do not cause prolonged downtime.

#### Acceptance Criteria

1. THE Dashboard SHALL be configured in `ecosystem.config.js` with a `max_memory_restart` threshold of 300 MB.
2. WHEN the Dashboard process exceeds 300 MB of memory, PM2 SHALL automatically restart the process.
3. THE Installer SHALL register the PM2 process with `pm2 startup` so the Dashboard restarts after a VPS reboot.
4. THE Dashboard SHALL log all HTTP requests using `morgan` in combined format to standard output.
5. WHEN `NODE_ENV` is set to `production`, THE Dashboard SHALL suppress detailed error stack traces from HTTP responses and log them to the PM2 log file instead.
